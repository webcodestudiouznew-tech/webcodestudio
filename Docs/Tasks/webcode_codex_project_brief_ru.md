# ТЗ для Codex: мультиязычный Project Brief WebCode

## 1. Цель задачи

Реализовать в существующем проекте WebCode собственный мультиязычный первичный бриф для клиентов.

Бриф должен быть частью сайта WebCode, работать на трёх языках и помогать собрать данные, необходимые для:

- понимания бизнеса клиента;
- определения задачи сайта;
- понимания продукта / услуг;
- понимания целевой аудитории;
- оценки объёма проекта;
- выявления нестандартного функционала;
- предварительной внутренней квалификации проекта;
- подготовки следующего шага: структура сайта, предложение и стоимость.

Бриф не должен выглядеть как сторонняя форма или классическое техническое задание.

---

## 2. Перед началом разработки

Сначала изучить существующий репозиторий и определить:

- используемый framework;
- текущую структуру routing;
- существующие UI-компоненты;
- design tokens;
- типографику;
- responsive breakpoints;
- текущую систему локализации;
- существующие RU / UZ / EN словари;
- API или backend для отправки заявок;
- CRM-интеграции;
- Telegram-уведомления;
- WhatsApp-ссылки;
- текущую систему аналитики;
- Privacy Policy route;
- текущие механизмы защиты форм от спама.

Нельзя создавать параллельную архитектуру, если в проекте уже есть подходящий механизм.

Нужно максимально переиспользовать существующую инфраструктуру WebCode.

---

## 3. Route

Добавить новый раздел:

`/brief`

Использовать текущую locale-routing архитектуру проекта.

Бриф должен поддерживать:

- русский;
- O‘zbekcha;
- English.

Не создавать три независимые формы.

Должна быть одна общая структура формы и отдельные языковые словари.

Все внутренние ключи вопросов и ответов должны быть независимы от языка.

Пример:

```ts
business_description
```

а не:

```ts
business_description_ru
business_description_uz
business_description_en
```

---

## 4. UX и внешний вид

Бриф должен быть реализован как пошаговый wizard.

Основные требования:

- mobile-first;
- визуально полностью соответствовать WebCode;
- минимальный header;
- логотип WebCode;
- переключатель языка RU / UZ / EN;
- progress indicator;
- кнопки «Назад» и «Продолжить»;
- закрытые вопросы оформлять как крупные selectable cards;
- textarea использовать только там, где нужен свободный ответ;
- понятные состояния hover / selected / focus / error;
- корректная keyboard navigation;
- плавные, но сдержанные transitions;
- без лишних анимаций;
- без основной навигации сайта;
- без внешнего вида стороннего form-builder;
- корректная работа на мобильных, планшетах и desktop.

Целевая длительность заполнения:

**4–6 минут.**

# 10. Сохранение прогресса

При случайном refresh пользователь не должен терять уже введённые ответы.

Реализовать локальное сохранение draft.

После успешной отправки draft удалить.

Контактные данные хранить локально только если это действительно необходимо.

Не сохранять чувствительные данные дольше, чем требуется.

# 12. Отправка данных

Максимально использовать существующую backend / lead-инфраструктуру WebCode.

При успешной отправке:

1. сохранить полный бриф;
2. связать его с `leadId`, если он передан;
3. отправить внутреннее уведомление через существующую инфраструктуру;
4. сформировать читаемый summary для команды WebCode;
5. вычислить внутренний `package_candidate`;
6. показать success screen.

# 14. Внутренняя квалификация проекта

Клиенту результат квалификации не показывать.

Допустимые значения:

```ts
launch
trust
growth
custom_review
```

Не использовать LLM для v1.

Квалификация должна быть deterministic.

---

## Launch candidate

Примерные признаки:

- один основной продукт / услуга;
- небольшой объём;
- одностраничный формат;
- нет сложного функционала;
- простая структура.

---

## Trust candidate

Примерные признаки:

- несколько услуг;
- нужен подробный landing;
- важны кейсы / отзывы;
- нужна более сильная коммерческая подача;
- небольшой многостраничный сайт.

---

## Growth candidate

Примерные признаки:

- полноценный корпоративный сайт;
- много направлений;
- развитая структура;
- несколько отдельных страниц;
- дальнейшее развитие сайта.

---

## Custom review

Флаг ручной оценки должен иметь приоритет над обычной квалификацией.

Автоматически ставить `custom_review`, если выбрано:

- онлайн-оплата;
- личный кабинет;
- сложный каталог;
- калькулятор;
- внешняя интеграция;
- другой нестандартный функционал.

`package_candidate` является только внутренней рекомендацией.

Он не определяет окончательную стоимость проекта.

# 17. Security

Требования:

- API secrets не должны попадать на client;
- переиспользовать существующие server-side механизмы;
- использовать существующую anti-spam защиту;
- не добавлять CAPTCHA без необходимости;
- не добавлять новые зависимости без веской причины;
- не ломать существующую security architecture проекта.

---

# 18. Ошибки отправки

Если backend submission завершился ошибкой:

- не терять заполненные ответы;
- показать понятное localized error message;
- дать возможность повторить отправку;
- записать событие `brief_submit_failed`;
- не создавать дубли при повторной успешной отправке.

---

# 19. Accessibility

Обеспечить:

- keyboard navigation;
- focus states;
- корректные labels;
- aria attributes там, где они нужны;
- контраст текста и controls;
- понятные validation messages;
- работу без обязательной мыши.

---

# 20. Responsive

Проверить минимум:

- mobile;
- tablet;
- desktop.

Особое внимание:

- длинным английским текстам;
- длинным узбекским текстам;
- selectable cards;
- progress bar;
- кнопкам Back / Continue;
- textarea;
- переключателю языка.

---

# 21. Что НЕ делать в v1

Не добавлять без отдельной задачи:

- AI-анализ ответов;
- автоматическую генерацию структуры сайта;
- генерацию коммерческого предложения;
- полноценный клиентский кабинет;
- сложный file manager;
- отдельную admin-панель;
- CMS-конструктор вопросов;
- LLM-квалификацию;
- сложные интеграции, которых пока нет в WebCode.

Цель v1 — надёжный, быстрый и красивый первичный бриф.

# 25. Ключевой продуктовый принцип

Бриф не является техническим заданием для клиента.

Клиент должен рассказать:

- о своём бизнесе;
- о продукте;
- о клиентах;
- о целях;
- о материалах;
- о сроках;
- о специальных требованиях.

Клиент не должен проектировать сайт самостоятельно.

WebCode самостоятельно определяет:

- рекомендуемый формат сайта;
- структуру;
- секции;
- UX;
- тексты;
- технологический подход;
- необходимый объём;
- итоговую стоимость.
